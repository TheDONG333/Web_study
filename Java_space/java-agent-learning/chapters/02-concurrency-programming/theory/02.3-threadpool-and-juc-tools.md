# 02.3 线程池与 JUC 高频工具

> **学习目标**
> - 透彻理解 ThreadPoolExecutor 七大核心参数
> - 掌握线程池的拒绝策略与常用场景
> - 熟练使用 ConcurrentHashMap 等 JUC 高频工具
> - 理解 CountDownLatch、volatile 等协作机制

---

## 1. 概述

直接 `new Thread()` 开销大且不受控制，**线程池**是管理线程的"容器"。同时，JUC（java.util.concurrent）提供了大量并发工具类，能让我们优雅地解决大多数并发问题。

---

## 2. 线程池核心架构

### 2.1 为什么用线程池？

| 对比 | 直接 new Thread | 线程池 |
|------|----------------|--------|
| 创建/销毁开销 | 每次创建，性能差 | 复用已创建的线程 |
| 线程数量控制 | 无限制，容易耗尽资源 | 精确控制最大并发数 |
| 管理能力 | 无 | 任务队列、拒绝策略、统计监控 |
| 响应速度 | 慢（需要重新创建线程） | 快（线程已就绪） |

### 2.2 ThreadPoolExecutor 七大核心参数

```java
public ThreadPoolExecutor(
    int corePoolSize,       // ① 核心线程数（常驻线程数量）
    int maximumPoolSize,    // ② 最大线程数（线程池能达到的最大数量）
    long keepAliveTime,     // ③ 空闲线程存活时间（超过 corePoolSize 的空闲线程的存活时间）
    TimeUnit unit,          // ④ 时间单位
    BlockingQueue<Runnable> workQueue,  // ⑤ 工作队列（存储等待执行的任务）
    ThreadFactory threadFactory,        // ⑥ 线程工厂（创建线程的工厂，可自定义线程名等）
    RejectedExecutionHandler handler    // ⑦ 拒绝策略（队列和线程都满了时的处理方式）
)
```

### 2.3 参数工作流程

```
提交任务
    │
    ▼
① 当前线程数 < corePoolSize？
    ├─ 是 → 创建新线程执行任务
    └─ 否 →
           │
           ▼
② 尝试放入工作队列
    ├─ 队列未满 → 放入队列等待
    └─ 队列已满 →
           │
           ▼
③ 当前线程数 < maximumPoolSize？
    ├─ 是 → 创建新临时线程执行任务
    └─ 否 →
           │
           ▼
④ 执行拒绝策略
```

**流程图解：**
```
                    ┌─────────────────────┐
                    │  提交任务到线程池      │
                    └──────────┬──────────┘
                               │
                    ┌──────────▼──────────┐
               YES  │ corePoolSize 满了吗？ │  NO
          ┌─────────│ (线程数 < corePool)?  │──────────┐
          │         └─────────────────────┘          │
          ▼                                          ▼
    ┌─────────────────┐                     ┌─────────────────┐
    │ 创建核心线程执行    │                     │  放入工作队列     │
    └─────────────────┘                     └────────┬────────┘
                                                     │
                                          ┌──────────▼──────────┐
                                     NO   │  队列满了吗？        │  YES
                                   ┌──────│                      │──────┐
                                   │      └─────────────────────┘      │
                                   ▼                                  ▼
                             ┌─────────────────┐            ┌─────────────────┐
                             │ 等待核心线程执行   │            │ maximumPoolSize  │
                             │（FIFO出队）       │       NO   │ 满了吗？         │  YES
                             └─────────────────┘      ┌─────│                  │──────┐
                                                       │     └─────────────────┘      │
                                                       ▼                            ▼
                                                 ┌─────────────────┐      ┌─────────────────┐
                                                 │ 创建临时线程执行    │      │ 执行拒绝策略      │
                                                 └─────────────────┘      └─────────────────┘
```

### 2.4 四种拒绝策略

| 策略 | 类名 | 行为 | 适用场景 |
|------|------|------|---------|
| **直接抛出异常** | `AbortPolicy` | 直接抛出 RejectedExecutionException | 默认策略，需要明确知道任务被拒绝 |
| **调用者自己执行** | `CallerRunsPolicy` | 任务由提交任务的线程自己执行 | 降级策略，减缓任务提交速度 |
| **丢弃最旧任务** | `DiscardOldestPolicy` | 丢弃队列中最旧的任务，然后尝试提交新任务 | 任务时效性强的场景 |
| **丢弃当前任务** | `DiscardPolicy` | 默默丢弃当前任务，不做任何通知 | 允许丢弃非关键任务 |

## 3. 常用线程池场景

### 3.1 几种 Executors 创建的线程池

#### FixedThreadPool（固定大小线程池）

```java
// 固定 4 个线程
ExecutorService fixed = Executors.newFixedThreadPool(4);

// 参数：corePoolSize=4, maximumPoolSize=4
//        keepAliveTime=0, workQueue=LinkedBlockingQueue（无界队列）
```

> 适用于：负载较重、任务数量稳定的场景。

#### CachedThreadPool（缓存线程池）

```java
ExecutorService cached = Executors.newCachedThreadPool();

// 参数：corePoolSize=0, maximumPoolSize=Integer.MAX_VALUE
//        keepAliveTime=60s, workQueue=SynchronousQueue（直接交付）
```

> 适用于：大量短时任务、任务提交速度快的场景。
> ⚠️ 最大线程数无限，任务量大时会创建大量线程，可能导致 OOM。

#### SingleThreadExecutor（单线程池）

```java
ExecutorService single = Executors.newSingleThreadExecutor();

// 参数：corePoolSize=1, maximumPoolSize=1
//        workQueue=LinkedBlockingQueue（无界队列）
```

> 适用于：需要顺序执行任务的场景（如日志写入）。

#### ScheduledThreadPool（定时线程池）

```java
ScheduledExecutorService scheduled = Executors.newScheduledThreadPool(4);

// 延迟执行
scheduled.schedule(() -> System.out.println("延迟1秒"), 1, TimeUnit.SECONDS);

// 周期性执行（固定频率）
scheduled.scheduleAtFixedRate(() -> System.out.println("每2秒一次"), 0, 2, TimeUnit.SECONDS);
```

### 3.2 为什么不推荐 Executors？

> **《阿里巴巴 Java 开发手册》强制规定**：不允许使用 Executors 创建线程池，应通过 ThreadPoolExecutor 手动配置。

```java
// ❌ 危险方式：可能 OOM
ExecutorService fixed = Executors.newFixedThreadPool(10);  // 无界队列！
ExecutorService cached = Executors.newCachedThreadPool();  // 无限线程！

// ✅ 推荐方式：手动配置
ExecutorService pool = new ThreadPoolExecutor(
    4,                      // corePoolSize
    8,                      // maximumPoolSize
    60L, TimeUnit.SECONDS,  // keepAliveTime
    new ArrayBlockingQueue<>(1000),  // 有界队列！
    Executors.defaultThreadFactory(),
    new ThreadPoolExecutor.CallerRunsPolicy()
);
```

## 4. JUC 高频工具

### 4.1 ConcurrentHashMap

> 线程安全的 HashMap，但不锁整个表。

```java
// 创建
ConcurrentHashMap<String, String> map = new ConcurrentHashMap<>();

// 常用方法
map.put("key", "value");
map.get("key");
map.remove("key");

// 原子复合操作（重要！）
map.putIfAbsent("key", "value");    // 不存在才放入
map.computeIfAbsent("key", k -> computeExpensiveValue(k));  // 不存在则计算
map.merge("key", "value", (old, val) -> old + "," + val);   // 合并

// 遍历（弱一致性：遍历时修改不会抛 ConcurrentModificationException）
for (String key : map.keySet()) {
    System.out.println(key + ": " + map.get(key));
}
```

**ConcurrentHashMap vs Hashtable vs Collections.synchronizedMap：**

| 对比 | Hashtable | synchronizedMap | ConcurrentHashMap |
|------|-----------|-----------------|-------------------|
| **锁粒度** | 锁整个表 | 锁整个表 | **锁分段**（JDK 7）/ **CAS + 红黑树**（JDK 8+） |
| **并发性能** | 极差 | 差 | 优 |
| **迭代器** | 强一致性（fail-fast） | 强一致性（fail-fast） | **弱一致性**（不会抛异常） |
| **允许 null** | ❌ 不允许 key/value | ✅ 允许 | ❌ 不允许 key/value |

### 4.2 CountDownLatch（倒计时门闩）

> 让一个或多个线程等待，直到其他线程完成指定数量的操作。

```java
public class CountDownLatchDemo {
    public static void main(String[] args) throws Exception {
        int workerCount = 3;
        CountDownLatch latch = new CountDownLatch(workerCount);

        // 启动 3 个工作线程
        for (int i = 0; i < workerCount; i++) {
            new Thread(() -> {
                System.out.println(Thread.currentThread().getName() + " 开始工作");
                try {
                    Thread.sleep((long) (Math.random() * 1000));
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
                System.out.println(Thread.currentThread().getName() + " 工作完成");
                latch.countDown();  // 计数器减 1
            }).start();
        }

        // 主线程等待所有工作线程完成
        System.out.println("主线程等待所有工作完成...");
        latch.await();  // 阻塞直到计数器归零
        System.out.println("所有工作完成，主线程继续执行");
    }
}
```

### 4.3 CyclicBarrier（循环屏障）

> CountDownLatch 的增强版：可重用，且所有线程到达屏障后可以同时执行后续操作。

```java
CyclicBarrier barrier = new CyclicBarrier(3, () -> {
    System.out.println("所有线程都已到达屏障，开始汇总");
});

// CountDownLatch vs CyclicBarrier
// CountDownLatch：一个线程等 N 个线程完成
// CyclicBarrier：N 个线程互相等待，到达屏障后同时继续
```

### 4.4 volatile 关键字

> 保证可见性 + 禁止指令重排序，但不保证原子性。

```java
public class VolatileDemo {
    // 适用场景：状态标志位
    private volatile boolean running = true;

    public void run() {
        while (running) {  // 每次读取从主内存获取最新值
            // 执行业务逻辑
        }
    }

    public void stop() {
        running = false;  // 修改立即对其他线程可见
    }
}
```

| 特性 | 说明 |
|------|------|
| ✅ **保证可见性** | 每次读取从主内存读，每次写入立即刷到主内存 |
| ❌ **不保证原子性** | `volatile int i++;` 仍然不安全 |
| ✅ **禁止重排序** | 内存屏障阻止指令重排 |
| 适用场景 | 状态标志位、单例模式双重检查锁中的 instance 字段 |

### 4.5 Semaphore（信号量）

> 控制同时访问特定资源的线程数量（限流）。

```java
public class SemaphoreDemo {
    // 最多允许 3 个线程同时访问
    private final Semaphore semaphore = new Semaphore(3);

    public void accessResource() {
        try {
            semaphore.acquire();  // 获取许可
            System.out.println(Thread.currentThread().getName() + " 正在访问资源");
            Thread.sleep(1000);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        } finally {
            semaphore.release();  // 释放许可
        }
    }
}
```

### 4.6 Atomic 原子类

> 基于 CAS（Compare-And-Swap）的无锁线程安全操作。

```java
// 基本类型
AtomicInteger count = new AtomicInteger(0);
count.incrementAndGet();     // 自增，返回新值：等价于 ++count
count.getAndIncrement();     // 自增，返回旧值：等价于 count++
count.addAndGet(10);         // 加 10
count.compareAndSet(50, 100);// 如果当前值为50，则设为100

// 引用类型
AtomicReference<String> ref = new AtomicReference<>("hello");
ref.compareAndSet("hello", "world");

// 性能对比（约 10 倍差距）
// AtomicInteger → 乐观锁（CAS，无阻塞，性能高）
// synchronized → 悲观锁（阻塞，性能较低）
```

## 5. 实战对比：CountDownLatch vs CyclicBarrier vs Semaphore

| 工具 | 核心用途 | 是否可重用 | 典型场景 |
|------|---------|-----------|---------|
| `CountDownLatch` | 等待 N 个事件完成 | ❌ 否 | 主线程等待所有子任务完成 |
| `CyclicBarrier` | N 个线程互相等待 | ✅ 是 | 分阶段并行计算 |
| `Semaphore` | 控制并发数量 | ✅ 是 | 限流、连接池管理 |

---

## 6. 关键要点总结

| 要点 | 说明 |
|------|------|
| ✅ 手动创建 ThreadPoolExecutor，明确参数 | 避免 Executors 的无界队列/无线程陷阱 |
| ✅ 理解线程池的"满则扩"流程 | core → queue → max → reject |
| ✅ ConcurrentHashMap 是并发首选 Map | 比 Hashtable/synchronizedMap 性能好得多 |
| ✅ volatile 只保证可见性，不保证原子性 | 适合标志位，不适合计数器 |
| ✅ CountDownLatch 一次性，CyclicBarrier 可重用 | 根据场景选择（一次等待 vs 循环屏障） |
