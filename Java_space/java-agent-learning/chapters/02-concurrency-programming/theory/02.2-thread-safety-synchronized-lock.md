## 1. 概述

多线程环境下，多个线程同时访问共享数据会导致数据不一致的问题——这就是**线程安全问题**。理解问题成因，掌握 synchronized 和 Lock 两种锁机制，是并发编程的核心能力。

---

## 2. 线程安全的根本成因

### 2.1 三大核心问题

```
线程安全问题的根源
        │
    ┌───┼───┐
    ▼   ▼   ▼
  原子性 可见性 有序性
```

### 2.2 原子性（Atomicity）

> **定义**：一个或多个操作要么全部完成且不被中断，要么全部不执行。

```java
// 经典问题：count++ 不是原子操作
count++;  // 实际分三步：读取 → 加1 → 写回

// 两个线程同时执行 count++：
// 线程1: 读取 count=0
// 线程2: 读取 count=0（线程1还没写回！）
// 线程1: count=1
// 线程2: count=1  （期望是2，实际得到1）
```

### 2.3 可见性（Visibility）

> **定义**：一个线程对共享变量的修改，另一个线程能立刻看到。

```java
boolean running = true;

// 线程1
while (running) {  // 可能永远看不到线程2的修改
    // 死循环！
}

// 线程2
running = false;   // 线程1可能看不到这个修改
```

**可见性问题的原因**：每个线程都有独立的工作内存（CPU 缓存），对共享变量的修改可能暂存在缓存中，没有立即刷新到主内存。

### 2.4 有序性（Ordering）

> **定义**：程序代码的执行顺序按照代码的先后顺序执行。

```java
int a = 0;
boolean flag = false;

// 线程1
a = 1;         // 语句1
flag = true;   // 语句2（可能被编译器重排序到语句1之前！）

// 线程2
if (flag) {
    System.out.println(a);  // 可能输出 0 而不是 1
}
```

**原因**：编译器和 CPU 为了优化性能，可能改变指令执行顺序（指令重排序），在单线程下不影响结果，但在多线程下可能导致意外结果。

### 2.5 核心解决思路

| 问题  | 解决方案       | Java 机制                            |
| --- | ---------- | ---------------------------------- |
| 原子性 | 加锁，让操作互斥执行 | synchronized、Lock、Atomic 类         |
| 可见性 | 强制刷新主内存    | volatile、synchronized、Lock         |
| 有序性 | 禁止指令重排序    | volatile、synchronized、Lock 都提供内存屏障 |

## 3. synchronized 关键字

### 3.1 三种用法

```java
public class SynchronizedDemo {

    // 方式1：同步实例方法（锁是 this 对象）
    public synchronized void method1() {
        // 同一时刻只能有一个线程执行此方法（同一对象）
    }

    // 方式2：同步静态方法（锁是 类.class 对象）
    public static synchronized void method2() {
        // 锁是 SynchronizedDemo.class
        // 所有实例共享这把锁
    }

    // 方式3：同步代码块（最灵活）
    public void method3() {
        // 普通场景
        synchronized (this) {
            // 锁 this
        }

        // 精确控制（用专门的锁对象）
        Object lock = new Object();
        synchronized (lock) {
            // 锁是 lock 对象
        }

        // 类锁
        synchronized (SynchronizedDemo.class) {
            // 锁是 类.class
        }
    }
}
```

### 3.2 synchronized 的底层原理

| 版本       | 实现机制                           | 说明                     |
| -------- | ------------------------------ | ---------------------- |
| JDK 6 之前 | 重量级锁（依赖 OS 互斥量 Mutex）          | 线程阻塞/唤醒涉及操作系统内核态切换，开销大 |
| JDK 6+   | **锁升级**：无锁 → 偏向锁 → 轻量级锁 → 重量级锁 | 大部分场景下锁竞争不激烈，避免内核切换    |

**锁升级过程：**

```
偏向锁 ──(竞争)──▶ 轻量级锁 ──(自旋失败)──▶ 重量级锁
  │                    │                       │
  └─ 只有一个线程访问   └─ 少量线程交替访问       └─ 多线程激烈竞争
```

### 3.3 面试高频：synchronized 的"可重入"特性

```java
public class ReentrantDemo {
    public synchronized void outer() {
        inner();  // 同一个线程可以再次获取同一把锁
    }

    public synchronized void inner() {
        // 不需要释放锁再重新获取
        // synchronized 会自动记录锁的持有次数
    }
}
```

> 可重入：同一个线程在持有锁的情况下，可以再次获取同一把锁而不会死锁。
> 
> **同一个线程，已经拿到了这把锁，还能再次进入这个锁包裹的同步代码，不会自己把自己卡死**

## 4. Lock 接口与 ReentrantLock

Lock是接口不能实例化，采用它的实现类ReentrantLock来实例化

### 4.1 Lock vs synchronized 的直观对比

```java
// synchronized 写法（自动）
synchronized (lock) {
    // 临界区
}
// 锁自动释放

// Lock 写法（手动）
Lock lock = new ReentrantLock();
lock.lock();
try {
    // 临界区
} finally {
    lock.unlock();   // 必须在 finally 中释放！
}
```

### 4.2 Lock 接口的独特能力

```java
public class LockFeaturesDemo {
    private final Lock lock = new ReentrantLock();

    // 1. 尝试获取锁（不阻塞）
    public void tryLockDemo() {
        if (lock.tryLock()) {           // 立即返回
            try {
                System.out.println("获取锁成功");
            } finally {
                lock.unlock();
            }
        } else {
            System.out.println("锁被占用，做其他事情");
        }
    }

    // 2. 尝试获取锁（带超时）
    public void tryLockWithTimeout() throws InterruptedException {
        if (lock.tryLock(1, TimeUnit.SECONDS)) {  // 最多等1秒
            try {
                System.out.println("1秒内获取到了锁");
            } finally {
                lock.unlock();
            }
        } else {
            System.out.println("1秒后仍未获取到锁");
        }
    }

    // 3. 可中断地获取锁
    public void lockInterruptiblyDemo() throws InterruptedException {
        lock.lockInterruptibly();  // 在等待锁的过程中可以被中断
        try {
            System.out.println("获取锁成功");
        } finally {
            lock.unlock();
        }
    }
}
```

### 4.3 ReentrantLock 的公平性

```java
// 非公平锁（默认）— 允许插队，吞吐量更高，谁抢到算谁的，不保证顺序
Lock unfairLock = new ReentrantLock();

// 公平锁 — 先等待的线程先获取锁，但性能稍低 严格遵守先来后到
Lock fairLock = new ReentrantLock(true);
```

### 4.4 ReadWriteLock 读写锁

- 读操作不修改数据，多个线程同时读完全没问题，没必要互相阻塞；
- 写操作会改数据，必须独占，读写、写写之间要互斥。

读写锁拆分两种锁：**读锁（共享锁）、写锁（排他锁）**，提升并发读性能。

```java
public class ReadWriteLockDemo {
    private final ReentrantReadWriteLock rwLock = new ReentrantReadWriteLock();
    private final Lock readLock = rwLock.readLock();
    private final Lock writeLock = rwLock.writeLock();
    private Map<String, Object> cache = new HashMap<>();

    // 读操作：多个线程可以同时读
    public Object get(String key) {
        readLock.lock();
        try {
            return cache.get(key);
        } finally {
            readLock.unlock();
        }
    }

    // 写操作：必须独占
    public void put(String key, Object value) {
        writeLock.lock();
        try {
            cache.put(key, value);
        } finally {
            writeLock.unlock();
        }
    }
}
```

> **读写锁规则**：读-读可并发，读-写互斥，写-写互斥。

## 5. synchronized vs Lock 对比总结

| 对比维度      | synchronized          | Lock (ReentrantLock)           |
| --------- | --------------------- | ------------------------------ |
| **语法**    | 关键字，自动获取/释放           | 接口，需手动 lock/unlock             |
| **锁释放**   | 自动释放（代码块结束或异常）        | **需在 finally 中显式释放**           |
| **可重入**   | ✅ 是                   | ✅ 是                            |
| **是否可中断** | ❌ 不可中断                | ✅ lockInterruptibly()          |
| **尝试获取锁** | ❌ 不支持                 | ✅ tryLock() / tryLock(timeout) |
| **公平性**   | ❌ 非公平                 | ✅ 可设置公平/非公平                    |
| **读写分离**  | ❌ 不支持                 | ✅ ReadWriteLock                |
| **条件等待**  | wait/notify（一套条件）     | Condition（多套条件，更灵活）            |
| **性能**    | JDK 6+ 优化后与 Lock 差距很小 | 高竞争场景仍稍好                       |
| **使用场景**  | 简单互斥，代码简洁             | 需要高级功能（超时、中断、公平、读写分离）          |

> **选择建议**：
> 
> - 大部分场景用 `synchronized` — 简单安全，JDK 6+ 性能已足够好
> - 需要 `tryLock` 超时、可中断、公平锁、读写锁等高级功能时用 `Lock`

## 6. volatile 关键字

### 6.1 volatile 的作用

```java
public class VolatileDemo {
    // volatile 保证可见性和禁止指令重排
    private volatile boolean running = true;

    public void run() {
        // 线程1：读取 running 的值
        while (running) {
            // 如果没有 volatile，这里可能永远看不到线程2的修改
        }
    }

    public void stop() {
        // 线程2：修改 running 的值
        running = false;
    }
}
```

### 6.2 volatile 能保证什么？

| 能力            | 说明                                   |
| ------------- | ------------------------------------ |
| ✅ **可见性**     | volatile 变量的修改会立即刷新到主内存，其他线程读取时从主内存读 |
| ✅ **禁止指令重排序** | volatile 操作前后的内存屏障阻止重排序              |
| ❌ **不保证原子性**  | `volatile count++` 仍然是线程不安全的！        |

### 6.3 volatile vs synchronized

| 对比    | volatile       | synchronized |
| ----- | -------------- | ------------ |
| 可见性   | ✅              | ✅            |
| 原子性   | ❌              | ✅            |
| 禁止重排序 | ✅              | ✅            |
| 性能开销  | 很小（没有锁）        | 相对较大         |
| 适用场景  | 单一变量的可见性，状态标志位 | 复合操作需要原子性    |

## 7. 代码示例：完整对比

```java
public class ThreadSafetyDemo {
    private int count = 0;

    // ❸ 三种方式对比
    public synchronized void incrementSync() {
        count++;
    }  // 同步：安全但串行化

    public void incrementWithLock() {
        lock.lock();
        try { count++; }
        finally { lock.unlock(); }
    }  // Lock：功能更丰富

    // ❌ 错误示例：volatile 不保证原子性
    private volatile int volatileCount = 0;
    public void incrementVolatile() {
        volatileCount++;  // 仍然线程不安全！
    }
}
```

## 8. 关键要点总结

| 要点                            | 说明                          |
| ----------------------------- | --------------------------- |
| ✅ 线程安全的三大根源：原子性 + 可见性 + 有序性   | 所有同步机制都为了解决这三个问题            |
| ✅ synchronized 是隐式锁，Lock 是显式锁 | synchronized 更简单，Lock 功能更强大 |
| ✅ JDK 6 后 synchronized 已大幅优化  | 先用 synchronized，不够再升级 Lock  |
| ✅ volatile 保证可见性，不保证原子性       | 适合标志位场景，不适合 count++         |
| ✅ 锁要尽量缩小范围                    | 只锁需要保护的代码，不要锁整个方法           |
