# 05.3 Spring 事务（超级重点）

> **学习目标**
> - 理解为什么需要事务、@Transactional 怎么用
> - 掌握事务传播行为（REQUIRED vs REQUIRES_NEW，面试必考）
> - 掌握事务隔离级别（脏读/不可重复读/幻读）
> - 掌握事务失效的常见场景（写业务天天踩坑）

---

## 1. 为什么需要事务？

### 白话理解

转账场景：A 扣 100 元，B 加 100 元。**两步必须同时成功或同时失败**——如果 A 扣完钱、B 加钱时报错了，钱就凭空消失了。

```java
// 没有事务：可能只执行了一半
public void transfer() {
    accountDao.decrease("A", 100);   // ① 扣钱成功
    // 💥 这里抛异常，② 没执行 → 钱没了！
    accountDao.increase("B", 100);   // ② 加钱
}
```

**事务（Transaction）** 保证：这一组操作"**要么全成，要么全败**"，失败时自动回滚（撤销已经做的操作）。

```
事务开始
  ① A 扣 100 元
  ② B 加 100 元
事务提交（全部成功，数据落库）
  ─── 或 ───
事务回滚（任何一步失败，①②全部撤销）
```

### 技术要点

- **四大特性（ACID）**：原子性（全成或全败）、一致性（数据合法）、隔离性（互不干扰）、持久性（落库不丢）
- 没框架时手写事务很麻烦（begin / commit / rollback），Spring 用 `@Transactional` 一个注解搞定

## 2. @Transactional 基本用法

### 白话理解

在方法上标一个注解，这个方法就是一个事务：方法内所有数据库操作要么全成、要么全败。

```java
@Service
public class AccountService {

    @Transactional                      // 标注：这个方法整体是一个事务
    public void transfer(String from, String to, double money) {
        accountDao.decrease(from, money);   // 扣钱
        accountDao.increase(to, money);     // 加钱
        // 方法执行完 → 提交
        // 中途抛异常 → 自动回滚
    }
}
```

**测试效果：**

```java
// 在 increase 前故意抛异常
@Transactional
public void transfer() {
    accountDao.decrease("A", 100);
    throw new RuntimeException("模拟转账失败");   // 抛出异常
    // accountDao.increase("B", 100);
}
```

> 运行后查看数据库：**A 的钱没有扣**——因为异常让整个事务回滚了。把 `@Transactional` 去掉再试，A 的钱就扣了。这就是事务的作用。

### 技术要点

- 默认**运行时异常（RuntimeException）回滚**，受检异常（Exception 子类）不回滚
- 作用在方法上；类上标注 = 该类的所有方法都有事务

## 3. 事务传播行为（面试必考）

### 白话理解

传播行为回答的问题是：**A 方法有事务，A 调用 B 方法，B 应该怎么处理？**

- 是加入 A 的事务（共用一个，同生共死）？
- 还是自己开一个新事务（独立提交）？

```java
// 场景：注册用户 = 插入用户 + 发优惠券
@Service
public class UserService {
    @Transactional
    public void register(User user) {
        userDao.insert(user);
        couponService.sendCoupon(user.getId());  // 调用另一个方法
    }
}
```

### 两种最常用的传播行为（必须背）

| 传播行为 | 白话理解 | 代码 |
|---------|---------|------|
| **REQUIRED**（默认） | 有事务就**加入**，没有就**新建**。内外共进退，一个失败全部回滚 | `@Transactional` 什么都不写就是它 |
| **REQUIRES_NEW** | **不管外面有没有，自己开一个全新事务**。外面的失败不影响自己 | `@Transactional(propagation = Propagation.REQUIRES_NEW)` |

**REQUIRED 效果：** 发优惠券失败 → 用户注册也回滚（一起死）

**REQUIRES_NEW 效果：** 发优惠券失败 → 用户已经注册成功（优惠券逻辑独立，不拖累注册）

### 完整传播行为速查表

| 传播行为 | 白话 |
|---------|------|
| `REQUIRED`（默认） | 加入已有事务，没有就新建 |
| `REQUIRES_NEW` | 总是开新事务，与外面无关 |
| `SUPPORTS` | 有事务就加入，没有就算了 |
| `NOT_SUPPORTED` | 强制不用事务执行 |
| `MANDATORY` | 必须已有事务，没有就报错 |
| `NEVER` | 必须没有事务，有就报错 |
| `NESTED` | 嵌套事务（类似保存点，部分回滚） |

> **面试重点**：能讲清楚 REQUIRED 和 REQUIRES_NEW 的区别 + 各举一个场景即可。

## 4. 事务隔离级别（面试必考）

### 白话理解

多个事务同时操作同一行数据时，可能互相干扰产生三种问题：

| 问题 | 白话理解 | 场景 |
|------|---------|------|
| **脏读** | 读到别人**还没提交**的数据（他回滚了你就读到假数据） | 读到事务 A 未提交的修改 |
| **不可重复读** | 同一次查询，两次结果**不一样**（期间被改了） | 读到已提交的更新 |
| **幻读** | 查询行数**变化**（期间被插入/删除） | 读到已提交的新行 |

### 隔离级别与解决程度

| 隔离级别 | 白话 | 解决脏读 | 解决不可重复读 | 解决幻读 |
|---------|------|:---:|:---:|:---:|
| `READ_UNCOMMITTED` | 啥都不防（几乎不用） | ❌ | ❌ | ❌ |
| `READ_COMMITTED` | 只能读已提交的（防脏读） | ✅ | ❌ | ❌ |
| `REPEATABLE_READ` | 同一事务内读取结果不变（MySQL 默认） | ✅ | ✅ | ❌（MySQL 实际解决了） |
| `SERIALIZABLE` | 事务排队执行，完全隔离（最安全最慢） | ✅ | ✅ | ✅ |

### 使用

```java
@Transactional(isolation = Isolation.REPEATABLE_READ)  // MySQL 默认级别
public void query() {
}
```

> **面试记住**：MySQL 默认 `REPEATABLE_READ`，能防脏读和不可重复读；`SERIALIZABLE` 最安全但性能最差。平时业务用默认即可，不需要特别设置。

## 5. 事务失效的常见场景（写业务天天踩坑！）

### 场景一：方法不是 public

```java
@Service
public class UserService {
    @Transactional
    private void addUser() {   // ❌ private 方法，代理进不去，事务失效
    }
}
```

> Spring 事务基于动态代理，**只有 public 方法才能被代理**。

### 场景二：同类内部调用（最常踩的坑！）

```java
@Service
public class UserService {

    // 外部调用这个：事务生效
    @Transactional
    public void register(User user) {
        // ❌ 直接调本类的 update 方法 = 内部自调用
        //    没走代理对象，@Transactional 根本不生效！
        this.updateUser(user);
    }

    @Transactional
    public void updateUser(User user) {
        // 这里的事务不会被注册生效
    }
}
```

> **原因**：`this.updateUser()` 调用的是**自己（原始对象）**，而事务要靠**代理对象**触发。内部调用绕过了代理 → 事务失效。

**解决方式：** 把需要事务的方法放到另一个类里调用（外部调用才走代理）。

### 场景三：异常被 try-catch 吞掉

```java
@Transactional
public void transfer() {
    try {
        accountDao.decrease("A", 100);
        throw new RuntimeException("失败");
    } catch (Exception e) {
        // ❌ 异常被吞了，Spring 以为方法正常执行完 → 不回滚！
        log.info("捕获异常但不处理");
    }
}
```

> **解决**：不要吞异常，或 catch 后再抛出去（或 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`，了解即可）。

### 场景四：抛出的不是运行时异常

```java
@Transactional
public void transfer() throws Exception {
    accountDao.decrease("A", 100);
    throw new Exception("受检异常");   // ❌ 默认不回滚！
    // 受检异常（Exception 子类）默认不回滚，只有 RuntimeException 回滚
}
```

> **解决**：`@Transactional(rollbackFor = Exception.class)`——写业务时**建议加上**，养成习惯：

```java
@Transactional(rollbackFor = Exception.class)   // 所有异常都回滚（推荐写法）
public void transfer() throws Exception {
}
```

### 场景五：类没被 Spring 管理

```java
public class UserService {     // ❌ 没有 @Service 注解
    @Transactional
    public void addUser() {
    }
}
```

> 不是 Bean，就没有代理，注解形同虚设。

### 失效场景总结表（背下来）

| # | 场景 | 白话 |
|---|------|------|
| 1 | 非 public 方法 | 代理进不去 |
| 2 | 同类内部调用（this.xxx） | 绕过了代理对象 |
| 3 | 异常被 catch 吞掉 | Spring 以为成功了 |
| 4 | 抛受检异常 | 默认只回滚 RuntimeException |
| 5 | 类没被 Spring 管理 | 没有代理 |

## 6. 关键要点总结

| 要点 | 说明 |
|------|------|
| ✅ @Transactional 一个注解搞定事务 | 方法内全成或全败 |
| ✅ 传播行为：REQUIRED 加入 / REQUIRES_NEW 新建 | 面试必考，重点背这两个 |
| ✅ 隔离级别：MySQL 默认 REPEATABLE_READ | 防脏读、不可重复读 |
| ✅ 事务失效五坑：非public/内部调用/吞异常/受检异常/非Bean | 写业务天天遇到 |
| ✅ 推荐写法：@Transactional(rollbackFor = Exception.class) | 养成习惯加上 |
