# 09.7 了解即可：BitMap / HyperLogLog / Geo

> **学习目标**（本节不要求写业务代码，只要求"遇到场景能想到它们"）
> - 知道这三个工具各自解决什么问题
> - 记住典型场景和大致效果，命令用时查文档

---

## 1. BitMap：用"一个 bit"记一个状态

### 白话理解

签到打卡：一个用户一年 365 天，如果每天存一条记录，一年 365 条。BitMap 的思路是——**每一天只用一个二进制位（0/1）**：

```
sign:user:1001  →  0 1 1 0 1 ...    （第 N 位 = 第 N 天签没签）
                    ↑ 位图：365 天只占约 46 字节
```

| 要点 | 说明 |
|------|------|
| 本质 | String 的每个 bit 当开关用 |
| 典型场景 | 签到打卡、活跃用户统计（日活/周活） |
| 效果 | 365 天的签到数据约 46 字节；1 亿用户日活统计内存占用极小 |
| 常见命令（用时查） | `setbit` / `getbit` / `bitcount` |

> **记忆**：数据只有"两种状态 + 量很大"（签到/打卡/是否活跃）→ 想到 BitMap。

## 2. HyperLogLog：海量数据的"大概有多少个"

### 白话理解

"今天有多少**不同**用户访问了首页（UV）"——用 Set 存每个用户 ID 也能算，但上千万用户内存吃不消。HyperLogLog 是**基数统计**工具：用约 **12KB** 内存，估算出"大概有多少个不同值"，**误差约 0.81%**。

```
Set 精确统计 100 万 UV  → 占几十 MB
HyperLogLog 估算 100 万  → 固定 12KB，误差 ±0.81%
```

| 要点 | 说明 |
|------|------|
| 本质 | 概率算法，用极少内存估算去重后的数量 |
| 典型场景 | UV 统计、海量去重计数 |
| 代价 | 不精确（误差 0.81%）；只能算个数，不能取明细 |
| 常见命令（用时查） | `pfadd` / `pfcount` / `pfmerge` |

> **选择标准**：数字是给老板看趋势的（UV、访问量）→ HyperLogLog；数字要对账（订单数）→ 老实用计数或数据库。

## 3. Geo：存地理位置，算"附近的人"

### 白话理解

外卖/打车界面的"**附近的店**"——把经纬度存进 Redis，一条命令算出半径内的目标，还能算距离。

```bash
geoadd shop:location 116.40 39.90 "店A"       # 存经纬度
geodist shop:location "店A" "店B" km          # 两家店距离（公里）
geosearch shop:location FROMLONLAT 116.41 39.91 BYRADIUS 3 km ASC   # 3 公里内的店
```

| 要点 | 说明 |
|------|------|
| 本质 | ZSet 的一种特殊编码（geohash），按位置排序 |
| 典型场景 | 附近的人 / 附近的店 / 打车派单 |
| 常见命令（用时查） | `geoadd` / `geodist` / `geosearch` |

> **边界**：小规模够用；复杂空间查询（多边形、路径规划）用专业地理方案（PostGIS、地图服务商 API）。

## 4. 三个工具一张表记住

| 工具 | 解决什么 | 场景 | 一句话记忆 |
|------|---------|------|-----------|
| BitMap | 状态存储超省内存 | 签到、活跃统计 | 两种状态 + 数据量大 |
| HyperLogLog | 海量去重计数 | UV 统计 | 只要个大概数 |
| Geo | 地理位置计算 | 附近的人/店 | 经纬度 + 半径查询 |

> **本阶段的态度**：不背命令、不写复杂业务代码——**面试/工作聊到"你会怎么统计 UV / 做附近的人"，能立刻说出"用 HyperLogLog / Geo"，这一节就合格了。** 真用到时查官方文档即可。

## 5. 关键要点总结

| 要点 | 说明 |
|------|------|
| ✅ BitMap | 一个 bit 一个状态，签到/活跃统计极省内存 |
| ✅ HyperLogLog | 12KB 估个数，误差 0.81%，UV 统计神器 |
| ✅ Geo | 经纬度存储 + 半径查询，附近的人/店 |
