# 10.4 Topic 交换机：通配符匹配（最灵活、最常用）

> **学习目标**
> - 掌握 Topic 的两个通配符：`*` 和 `#`，能说出区别
> - 会设计路由键（用点号分层）和绑定规则
> - 能根据业务在 Direct / Fanout / Topic 之间做选择
> - 知道 Headers 交换机是什么、为什么几乎不用

---

## 1. 白话理解：Topic 是"会看模式"的分拣员

Direct 要求地址**一字不差**，Fanout **完全不看**地址。Topic 介于两者之间：**按模式匹配**。

- 路由键用 **`.`（点）** 分段：`order.pc.create`
- 绑定规则里可以用**两个通配符**来匹配这些段

```
order.pc.create
      │  │   └── 第 3 段
      │  └────── 第 2 段
      └───────── 第 1 段
```

---

## 2. 两个通配符（必背）

| 通配符 | 含义 | 白话 |
|--------|------|------|
| `*`（星号） | 匹配**恰好一个**单词（一段） | "这一段随便是什么，但必须有一段" |
| `#`（井号） | 匹配**零个或多个**单词 | "后面是什么都行，没有也行" |

### 对照例子：绑定 `order.*.create`

| 消息路由键 | 是否匹配 | 原因 |
|-----------|---------|------|
| `order.pc.create` | ✅ | 中间段 `pc` 被 `*` 匹配 |
| `order.app.create` | ✅ | 中间段 `app` 被 `*` 匹配 |
| `order.create` | ❌ | 只有 2 段，`*` 少一段可匹配 |
| `order.pc.pay.create` | ❌ | 4 段，`*` 只能顶 1 段 |
| `order.pc.pay` | ❌ | 结尾不是 create |

### 对照例子：绑定 `order.#`

| 消息路由键 | 是否匹配 | 原因 |
|-----------|---------|------|
| `order.create` | ✅ | `#` 匹配 1 段 |
| `order.pc.create` | ✅ | `#` 匹配 2 段 |
| `order.pc.pay.create` | ✅ | `#` 匹配 3 段 |
| `order` | ✅ | `#` 匹配 **0 段**（容易忽略！） |
| `user.create` | ❌ | 开头不是 order |

> **记忆**：`*` 是"**一段**"，`#` 是"**任意段（含零段）**"。

---

## 3. 一个完整的业务例子：日志路由

需求：
- 所有订单相关日志 → 审计队列
- 所有服务的 error 日志 → 告警队列
- 订单创建日志 → 统计队列

**路由键设计**：`服务.模块.级别`，如 `order.pc.create`、`order.pc.error`、`user.app.error`

**绑定设计**：

```
交换机 ex.log (topic)
├── 绑定 order.#      ──▶ 队列 q.audit      （所有订单日志）
├── 绑定 #.error      ──▶ 队列 q.alert      （所有服务的 error）
└── 绑定 order.*.create ─▶ 队列 q.stat      （订单创建）
```

**验证**：

| 发送路由键 | q.audit | q.alert | q.stat |
|-----------|---------|---------|--------|
| `order.pc.create` | ✅ | ❌ | ✅ |
| `order.pc.error` | ✅ | ✅ | ❌ |
| `user.app.error` | ❌ | ✅ | ❌ |
| `order.create` | ✅ | ❌ | ❌（`*` 需要 3 段） |

> 一条消息可以被**多个队列同时收到**（只要各自绑定规则都匹配）——这是 Topic 强大的地方。

---

## 4. 三种交换机对比与选择

| | Direct | Fanout | Topic |
|---|--------|--------|-------|
| 匹配方式 | 完全相等 | 不看路由键，全发 | 通配符模式匹配 |
| 路由键设计 | 简单单词 | 可忽略 | **点号分层**（如 `order.pc.create`） |
| 灵活性 | 低 | 低 | **高** |
| 性能 | 最高 | 最高 | 略低（可忽略） |
| 典型场景 | 按类型精确分流 | 广播通知 | 多维度订阅、日志、事件总线 |

**选择口诀**：

```
只需要"是/不是"      → Direct
需要"所有人都知道"    → Fanout
需要"按维度组合订阅"  → Topic
```

> 实际项目里 **Topic 用得最多**：因为业务需求经常变（"既要按服务订阅，又要按级别订阅"），Topic 的绑定规则可以随时加，不用改生产者。

---

## 5. Headers 交换机（了解即可）

Headers 交换机**不看路由键，看消息头（headers）**里的键值对。绑定规则里指定"匹配哪些 header"，并支持 `x-match: all`（全部匹配）或 `any`（任一匹配）。

```
❌ 为什么几乎不用：
- 配置比 Topic 复杂得多
- 可读性差（消息头里塞一堆键值对）
- 性能不如 Direct / Topic
- 绝大多数场景 Topic 都能替代
```

> 面试问到时一句话回答："Headers 按消息头匹配，灵活性不如 Topic 且性能较差，生产几乎不用。"

---

## 6. 关键要点总结

| 要点 | 说明 |
|------|------|
| ✅ `*` | 匹配恰好一段 |
| ✅ `#` | 匹配零段或多段（`order.#` 也匹配 `order`） |
| ✅ 路由键用点分层 | `服务.模块.级别`，绑定规则才好玩 |
| ✅ Topic 最常用 | 多维度订阅，绑定可随时扩展，生产者不动 |
| ✅ 一条消息可进多队列 | 多条绑定同时匹配即可 |
| ✅ Headers | 按消息头匹配，复杂且性能差，了解即可 |
