# 07.1 SSM 整合全景：三个框架如何协作

> **学习目标**
> - 理解 Spring / SpringMVC / MyBatis 各管哪一层
> - 掌握三份配置文件的职责划分
> - 看懂一个请求在 SSM 中的完整流转
> - 理解这套分层结构就是 Spring Boot 的骨架

---

## 1. 三个框架各管什么？

### 白话理解

前六章你已经分别学完三个框架。SSM 整合就是把它们拼成一个完整的 web 项目，**各管一段，互不越界**：

| 框架 | 管什么 | 白话 |
|------|--------|------|
| **SpringMVC** | web 层：接请求、回响应 | 前台接待 |
| **Spring** | 业务层：管对象、AOP、事务 | 业务经理 |
| **MyBatis** | 数据层：操作数据库 | 仓库管理员 |

```
浏览器请求
   │
   ▼
SpringMVC（web 层）──▶ Spring（业务层）──▶ MyBatis（数据层）──▶ MySQL
   Controller              Service              Mapper
```

> **一句话**：请求从 Controller 进、经 Service 转、由 Mapper 落地到数据库——**分层思想在 Spring Boot 里一模一样**，只是配置方式从 XML 变成了自动装配。

## 2. 三份配置文件：各司其职

### 白话理解

整合后共有三份 Spring 配置文件（`web.xml` 是 Servlet 容器配置，不算 Spring 的）：

| 配置文件 | 扫描哪些包 | 管什么 |
|---------|-----------|--------|
| **spring-context.xml** | `com.demo.service` / `mapper` 等**非 controller** | IOC、数据源、SqlSessionFactory、Mapper 扫描、**事务** |
| **spring-mvc.xml** | `com.demo.controller` | Controller 扫描、注解驱动、视图解析器、拦截器 |
| **mybatis-config.xml** | 无（mapper.xml 单独） | MyBatis 全局设置（可选；整合后通常合并进 spring-context.xml） |

### 为什么分成两份 Spring 配置？（面试常问）

```
spring-context.xml   = 父容器：管业务层（Service、Dao、事务）
spring-mvc.xml       = 子容器：管表现层（Controller）
```

- 分成两个容器，**职责清晰**：Service 归父管，Controller 归子管
- **关键点**：两个容器扫描的包不能重复——否则同一个类注册两次，会出问题
- 所以 spring-context.xml 扫 service/mapper，spring-mvc.xml 只扫 controller

### 配置对应关系（回忆前几章）

| 配置项 | 对应的章节知识 |
|--------|--------------|
| 数据源 + SqlSessionFactoryBean + MapperScannerConfigurer | 05.4 Spring 整合 MyBatis |
| `<tx:annotation-driven>` + @Transactional | 05.3 Spring 事务 |
| `<mvc:annotation-driven>` + @RestController | 06.x SpringMVC |
| InternalResourceViewResolver（返回 JSP） | 06.3 视图解析 |

> 整合没有新知识，就是把前两章学的配置**放到一个项目里**。这章真正练的是"排错能力"——配置一多，报错就多。

## 3. 一个请求的完整流转（整合后）

```
浏览器 GET /user/list?page=1
      │
      ▼
Tomcat → web.xml 里的 DispatcherServlet（总指挥）
      │
      ▼
spring-mvc.xml：HandlerMapping 找到 UserController.list()
      │
      ▼
UserController.list()（web 层：收参数）
      │ @Autowired 注入
      ▼
UserService.page(page, size)（业务层：调 Mapper）
      │ @Transactional（事务由 spring-context.xml 管理）
      ▼
UserMapper.page(offset, limit)（数据层：SQL）
      │
      ▼
MySQL 返回数据 → 逐层返回
      │
      ▼
UserController 把数据放进 Model → 返回视图名 "user/list"
      │
      ▼
ViewResolver 解析 → /WEB-INF/jsp/user/list.jsp 渲染 → 返回浏览器
```

> 对比记忆：这个流程 = 06.1 的 DispatcherServlet 流程 + 05.4 的 Mapper 注入 + 05.3 的事务，全部串起来。

## 4. 分层职责（本项目的铁律）

```
Controller(web 层)    只做：收参数、调 Service、放数据/回 JSON
Service(业务层)       只做：业务逻辑、事务（@Transactional）
Mapper(数据层)        只做：SQL 操作（不写业务逻辑）
```

**违反分层的典型错误**（写代码时对照自查）：

```java
// ❌ Controller 里直接调 Mapper（跳过 Service，事务和业务逻辑都丢了）
@Autowired
private UserMapper userMapper;   // Controller 不应该持有 Mapper！

// ✅ 正确：Controller → Service → Mapper
@Autowired
private UserService userService;
```

> **为什么重要**：Spring Boot 也是这套分层（Controller/Service/Mapper 包结构一模一样）。现在养成习惯，后面无缝过渡。

## 5. 为什么 SSM 配置很烦？为什么后来有 Spring Boot？

### 白话理解

整合一个 SSM 项目，你要手工写：

```
web.xml（DispatcherServlet 配置）
spring-context.xml（数据源、事务、MyBatis 整合）
spring-mvc.xml（扫描、视图、拦截器）
+ 一堆 Maven 依赖（版本还得自己对齐）
```

**配置本身不难，但版本对齐 + 排错非常折磨人**——这就是这章要你亲手踩坑的原因。

**Spring Boot 的答案**：**约定大于配置**——
- 依赖版本：starter 帮你管理好（`spring-boot-starter-web` 一个依赖搞定）
- 自动配置：写一个 `application.yml` 就有数据源和事务
- 内嵌 Tomcat：连部署都省了

> 学完这章你就能深刻理解：**Spring Boot 就是把 SSM 这套手工配置自动化了**。它们的分层结构完全一样。

---

## 6. 关键要点总结

| 要点 | 说明 |
|------|------|
| ✅ SpringMVC 管 web，Spring 管业务，MyBatis 管数据 | 各管一段，互不越界 |
| ✅ 两份 Spring 配置：父容器(业务) + 子容器(表现) | 扫描包不能重叠 |
| ✅ 请求流转：Controller → Service → Mapper | 事务在 Service 层 |
| ✅ 分层铁律：Controller 不碰 Mapper | 必须经 Service |
| ✅ Spring Boot = SSM 手工配置的自动化 | 分层结构完全一样 |
