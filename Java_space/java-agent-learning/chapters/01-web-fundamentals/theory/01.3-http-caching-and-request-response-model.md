# 01.3 HTTP 缓存机制与请求-响应模型

> **学习目标**
> 
> - 理解 HTTP 缓存的完整体系（强制缓存 vs 协商缓存）
> - 掌握请求-响应模型中客户端与服务器的交互本质
> - 能够从开发者工具中识别缓存命中情况

---

## 1. 概述

HTTP 缓存是 Web 性能优化的**第一道防线**。合理的缓存策略可以减少 60%-80% 的重复请求，极大提升页面加载速度。同时，理解"请求-响应"模型是理解整个 Web 通信的基础。

---

## 2. 请求-响应模型

1. 请求头 Request Headers：**附加描述信息，不带业务数据**
2. 请求体 Request Body：客户端传给服务器的**业务数据**
3. 响应头 Response Headers：**服务器告诉客户端「本次返回数据的附加规则、配置」**
4. 响应体 Response Body：**服务器真正返回给你的核心业务数据**

### 2.1 核心交互模型

HTTP 协议的工作方式异常简单：**客户端发请求，服务器给响应**。

```
┌──────────┐        1. 请求（Request）        ┌──────────┐
│          │ ───────────────────────────────▶ │          │
│  客户端  │                                  │  服务器  │
│ (浏览器) │ ◀─────────────────────────────── │          │
│          │        2. 响应（Response）        │          │
└──────────┘                                  └──────────┘
```

### 2.2 一次完整的请求-响应生命周期

```
① 建立 TCP 连接（三次握手）
  │
  ├─▶ ② 客户端发送 HTTP 请求报文
  │
  ├─▶ ③ 服务器处理请求
  │
  ├─▶ ④ 服务器返回 HTTP 响应报文
  │
  └─▶ ⑤ 客户端处理响应 + 关闭/复用连接（四次挥手或 keep-alive）
```

### 2.3 短连接 vs 长连接

| 特性  | 短连接（HTTP/1.0 默认）         | 长连接（HTTP/1.1 默认）         |
| --- | ------------------------ | ------------------------ |
| 行为  | 每次请求都新建 TCP 连接           | 复用同一 TCP 连接发送多个请求        |
| 头字段 | 无（或 `Connection: close`） | `Connection: keep-alive` |
| 性能  | 每次请求都有三次握手开销             | 减少握手次数，性能更好              |
| 适用  | 少量请求                     | 一个页面几十个资源（CSS/JS/图片）     |

### 2.4 客户端与服务器的交互本质

> **核心理解：服务器是无状态的，它只按请求返回响应。所有的"用户状态"（登录、购物车等）都需要通过附加机制来实现。**

| 机制          | 原理                                     | 典型应用     |
| ----------- | -------------------------------------- | -------- |
| **Cookie**  | 服务器在响应头 `Set-Cookie` 中种下标识，浏览器后续请求自动携带 | 保持登录态    |
| **Session** | 服务端存储用户数据，通过 Cookie 中的 SessionId 关联    | 购物车、用户信息 |
| **Token**   | 客户端持有经过签名的凭证，每次请求携带                    | JWT 认证   |

## 3. HTTP 缓存体系

### 3.1 缓存的两大类型

```
                    HTTP 缓存
                   /          \
           强制缓存            协商缓存
          (强制命中)          (需要验证)
               │                   │
    ┌──────────┴──────────┐    ┌──┴──┐
    │  Cache-Control      │    │ETag │
    │  Expires            │    │Last │
    │                     │    │-Modi│
    │                     │    │-fied│
    └─────────────────────┘    └─────┘
```

### 3.2 强制缓存（Strong Cache）

> 浏览器直接使用本地副本，**不发送请求到服务器**。

**相关头字段：**

| 头字段                           | 示例                                       | 说明                              |
| ----------------------------- | ---------------------------------------- | ------------------------------- |
| `Cache-Control: max-age=3600` | 缓存 3600 秒                                | **推荐**，优先级最高                    |
| `Cache-Control: no-cache`     | 不使用强制缓存                                  | （注意：no-cache 意思是"使用前先去验证"）      |
| `Cache-Control: no-store`     | 完全禁止缓存                                   | 敏感数据使用                          |
| `Expires`                     | `Expires: Tue, 21 Jul 2026 12:00:00 GMT` | 绝对过期时间（旧方式，优先级低于 Cache-Control） |

**强制缓存工作流程：**

```
浏览器请求资源 ──▶ 检查 Cache-Control: max-age
                        │
                    ┌───┴───┐
                    │ 未过期 │  ──▶ 直接从本地缓存读取（200 from disk/memory cache）
                    └───────┘
                        │ 过期
                        ▼
                    发送请求到服务器
```

> **开发者工具中的表现**：`200 OK (from disk cache)` 或 `200 OK (from memory cache)`

### 3.3 协商缓存（Negotiation Cache）

> 浏览器携带资源的"身份标识"向服务器验证，服务器判断资源是否修改。

**两种验证方式：**

| 方式       | 请求头                 | 响应头             | 说明             |
| -------- | ------------------- | --------------- | -------------- |
| **基于时间** | `If-Modified-Since` | `Last-Modified` | 不精确（秒级），可能遗漏   |
| **基于哈希** | `If-None-Match`     | `ETag`          | **推荐**，精确到内容变化 |

**协商缓存工作流程：**

```
浏览器有缓存但不确定是否过期
        │
        ▼
发送 GET 请求，携带：
  If-Modified-Since: Mon, 20 Jul 2026 12:00:00 GMT
  If-None-Match: "33a64df5"
        │
        ▼
服务器比对：
  ① 检查 If-None-Match 与当前 ETag 是否一致
  ② 检查 If-Modified-Since 与 Last-Modified
        │
    ┌───┴───┐
    │ 未修改 │  ──▶ 返回 304 Not Modified（无响应体）
    └───────┘
        │ 已修改
        ▼
    返回 200 OK + 新资源
```

> **开发者工具中的表现**：`304 Not Modified`（从服务器验证后使用缓存）

### 3.4 完整缓存决策流程

```
收到一个资源的 URL
        │
        ▼
    有本地缓存副本？
    ┌───┴───┐
    │  是   │       否
    ▼       │       ▼
  检查 max-age   直接请求服务器
  /Expires       （200 OK）
    │
  ┌─┴─┐
  │有效│ → 强制缓存命中（200 from cache）
  └───┘
    │ 已过期
    ▼
  发起请求，携带
  If-Modified-Since
  /If-None-Match
    │
  ┌─┴─┐
  │未修改│ → 协商缓存命中（304 Not Modified）
  └───┘
    │ 已修改
    ▼
  返回新资源（200 OK）
```

### 第 1 步：浏览器先查本地有没有缓存

打开网址瞬间，浏览器先在硬盘里翻：之前访问过这个地址，有没有存下对应的页面 / 接口 JSON、图片？

- 没缓存：直接跳到第 6 步，去找服务器拿新数据
- 有缓存：进入第 2 步，校验缓存还能不能用

### 第 2 步：看缓存有没有过期（强缓存判断）

缓存文件存的时候，服务器给它标了一个「保质期」，靠两个字段控制：

1. `Cache-Control: max-age=3600`：保质期 3600 秒（1 小时）
2. `Expires`：固定过期时间点（老标准，现在优先 Cache-Control）

计算逻辑：

当前时间 ＜ 过期时间 → **没过期，强缓存生效**

✅ 直接用本地缓存，**根本不发请求给服务器**，地址栏看不到网络请求，速度最快

当前时间 ＞ 过期时间 → 缓存过期，强缓存失效，进入第 3 步协商缓存

### 第 3 步：发一个「询问请求」给服务器（协商缓存）

缓存过期了，但不确定服务器那边文件有没有改动，浏览器不直接下载完整资源，只发一条轻量请求问服务器：

> 我本地有一份旧文件，你那边的文件更新了吗？

浏览器会带上两个标识二选一发给服务端：

1. `If-Modified-Since`：本地缓存上次修改的时间
2. `If-None-Match`：本地缓存的唯一指纹 ETag（更精准，优先用）

### 第 4 步：服务器核对文件，分两种结果

#### 分支 A：服务器文件**没改动**

服务器对比时间 / 指纹，发现内容和浏览器本地一模一样

返回状态码 `304 Not Modified`，**不返回完整文件数据**，只告诉浏览器：你本地缓存还能用

浏览器拿到 304 → 继续用本地缓存，同时刷新这份缓存的保质期，流程结束。

#### 分支 B：服务器文件**已经更新**

服务器对比后发现内容变了（页面改了、接口数据更新、图片替换）

返回状态码 `200 OK`，把**全新完整的数据**发给浏览器

### 第 5 步：浏览器拿到新数据，更新本地缓存

浏览器收下新页面 / 接口数据，同时读取响应头里新的保质期规则（Cache-Control、ETag、Last-Modified），覆盖硬盘里旧的缓存文件，下次访问再走这套判断。

### 第 6 步：完全无缓存的情况（第一次访问 / 缓存手动清空）

浏览器本地啥都没有，直接发送完整请求到服务器

服务器返回 200 + 完整资源，浏览器保存到本地缓存，标记过期时间，流程结束。

### 第 7 步：强制不走缓存（手动干预，打破上面所有规则）

两种场景会跳过全部缓存逻辑，直接请求服务器：

1. 用户强制刷新页面：`Ctrl+F5`，浏览器直接忽略本地缓存，不带协商标识，强行拉新数据

2. 资源设置禁止缓存：接口 / 页面响应头 `Cache-Control: no-cache / no-store`
   
   - no-cache：缓存可以存，但每次必须找服务器核对（不走强缓存，只走协商缓存）
   - no-store：完全禁止存缓存，每次都重新下载全新数据

## 极简串联总结（一句话走完流程）

打开网页 → 本地找缓存 → 没过期直接用；过期就问服务器文件改没改 → 没改动继续用旧缓存，改动了下载新缓存覆盖本地；强制刷新 / 禁止缓存则直接跳过本地缓存拿新数据。

## 补充区分两个容易搞混的词

1. **强缓存**：不跟服务器通信，直接本地读，最快
2. **协商缓存**：和服务器发轻量请求核对，不返回完整文件，比重新下载快，但比强缓存慢

### 3.5 缓存策略配置建议

| 资源类型          | 缓存策略                      | 原因             |
| ------------- | ------------------------- | -------------- |
| HTML 页面       | `no-cache`                | 内容经常变，但允许协商缓存  |
| CSS/JS（带版本哈希） | `max-age=31536000`（一年）    | 文件名哈希变了就相当于新文件 |
| 图片/字体         | `max-age=2592000`（30天）    | 不常变，缓存友好       |
| API 数据        | `no-cache` 或 `max-age=60` | 数据实时性要求高       |
| 敏感数据          | `no-store`                | 不缓存任何信息        |

## 4. 实战案例：分析一个页面的缓存

使用浏览器开发者工具（F12 → Network 面板），加载任意网页后：

1. 观察每个资源的 **Status** 列：
   
   - `200` → 从服务器获取的
   - `200 (disk cache)` → 强制缓存命中
   - `304` → 协商缓存命中

2. 观察 **Size** 列：
   
   - `(disk cache)` → 从磁盘缓存读取
   - `(memory cache)` → 从内存缓存读取
   - 具体数字 → 从服务器下载的大小

3. 观察 **Headers**：
   
   - 寻找 `Cache-Control`、`ETag`、`Last-Modified` 头字段

## 5. 关键要点总结

| 要点                          | 说明                                |
| --------------------------- | --------------------------------- |
| ✅ 请求-响应模型是 HTTP 的基础         | 客户端主动发请求，服务器被动响应                  |
| ✅ HTTP 默认无状态                | 状态需要 Cookie/Session/Token 等额外机制维持 |
| ✅ 强制缓存（200 from cache）不走服务器 | 用 Cache-Control: max-age 控制       |
| ✅ 协商缓存（304）需要验证             | 用 ETag/If-None-Match 控制           |
| ✅ 304 响应没有 Body             | 只告诉客户端"你还用旧的"                     |

## 7.强缓存与协商缓存

### 一、强缓存（不用问服务器，直接拿本地文件）

#### 大白话类比

你买了一箱零食，包装写保质期 1 年（对应`Cache-Control: max-age`）。保质期内想吃直接从家里拿，不用跑去超市采购；浏览器访问资源同理：在保质期以内，**完全不发请求给服务器**，直接读取内存 / 磁盘里存好的文件。

#### 技术细节

1. 判断依据：响应头`Cache-Control: max-age`（优先）、老旧字段`Expires`，规定缓存有效时长；
2. Network 表现：状态码`200（来自内存缓存/disk磁盘缓存）`；
3. 优缺点：速度最快，没有网络消耗；缺点是缓存没过期时，就算服务器更新文件，浏览器还是继续用旧本地文件；
4. 你的案例：百度 logo 设置`max-age=31536000`也就是缓存 1 年，一年内打开百度首页，浏览器直接读本地缓存图片，不访问百度服务器，就是典型强缓存。

### 二、协商缓存（先问服务器能不能继续用旧缓存）

#### 大白话类比

零食保质期到了，不确定超市有没有上新批次；你发消息问老板：之前那款零食还有吗、有没有改动？老板分两种答复：

①商品没改动：你继续吃家里剩下的就可以，不用买新的（服务器返回 304，浏览器继续用本地缓存）；

②商品已经换新批次：给你发新货，扔掉旧存货（服务器返回 200、下发全新资源，浏览器更新本地缓存）。

#### 技术细节

1. 触发条件：强缓存过期了，才会走协商缓存；
2. 浏览器会带上两个凭证询问服务器：`ETag`（文件指纹）、`Last-Modified`（文件修改时间）；
3. Network 表现：状态码`304 Not Modified`；服务器不传输完整文件，只告知旧缓存可用；
4. 优缺点：需要发一次很小的请求和服务器沟通，速度比强缓存慢、比重新下载整份文件快；能拿到最新资源变动，不会一直使用旧文件。
