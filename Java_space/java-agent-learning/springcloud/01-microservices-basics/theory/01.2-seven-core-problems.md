# 01.2 微服务七大核心问题：拆完之后要面对什么

> **学习目标**
> - 记住微服务七大核心问题（先背问题，不背组件）
> - 能说出每个问题"不解决会发生什么"
> - 理解每个问题对应的解决思路
> - 知道不是所有项目都需要全部七种能力

---

## 1. 白话理解：方法调用变成了"打电话"

单体里，用户服务调用订单服务就是一行代码：

```java
orderService.createOrder(userId);   // 同一个进程，几乎不会失败
```

拆成微服务后，这行代码变成了跨网络的 HTTP 请求：

```
用户服务 ──网络──▶ 订单服务
```

网络会超时、会断、对方可能部署在 3 台机器上、可能正在重启、可能突然涌进 10 倍流量……**原本不存在的问题，全是"拆"出来的。**

七大问题，就是拆完之后必须面对的新成本。

---

## 2. 七大问题总览

| # | 问题 | 不解决会怎样 | 解决思路 | 当前常用组件 |
|---|------|-------------|---------|-------------|
| 1 | 服务注册与发现 | 不知道对方在哪台机器 | 注册中心统一登记 | Nacos / Consul |
| 2 | 服务调用 | 手写 HTTP 太麻烦 | 声明式远程调用 | OpenFeign |
| 3 | 负载均衡 | 请求全压到一台实例 | 按策略分发请求 | Spring Cloud LoadBalancer |
| 4 | 熔断降级 | 一个服务挂，拖垮整条链路 | 断流 + 兜底 | Sentinel / Resilience4j |
| 5 | 网关路由 | 前端要记每个服务的地址 | 统一入口 + 路由 | Spring Cloud Gateway |
| 6 | 统一配置 | 配置散落、改配置要重启 | 集中管理 + 动态刷新 | Nacos Config |
| 7 | 分布式事务 | 跨服务数据不一致 | 最终一致性方案 | Seata |

> **本模块只需要记住"问题"和"解决思路"**，组件名后面模块会逐个展开。

---

## 3. 逐个说清

### ① 服务注册与发现

**问题**：订单服务有 3 台实例，IP 可能变（容器重建、扩容）。用户服务怎么知道该调哪个 IP？

**不解决**：把 IP 写死在配置文件里——对方一扩容或换机器，调用方全部失效。

**解决思路**：

```
服务启动时 → 向注册中心登记"我是订单服务，我在 10.0.0.3:8080"
调用方     → 问注册中心"订单服务有哪些实例？"
注册中心   → 返回实例列表（并持续健康检查）
```

**白话**：注册中心就是"**服务通讯录**"，谁上线谁登记，谁下线谁注销。

---

### ② 服务调用

**问题**：跨服务调用要拼 URL、发 HTTP、处理超时、解析 JSON、处理异常……每个调用都写一遍太痛苦。

**不解决**：业务代码里全是 `HttpClient` 样板代码，又长又容易错。

**解决思路**：声明式客户端——定义一个接口，像调本地方法一样调远程服务：

```java
@FeignClient("order-service")
public interface OrderClient {
    @GetMapping("/orders/{id}")
    Order getOrder(@PathVariable("id") Long id);
}
```

**白话**：把"打电话"包装成"喊一嗓子"，底层网络细节框架帮你处理。

---

### ③ 负载均衡

**问题**：订单服务有 3 台实例，用户服务的请求应该发给哪台？

**不解决**：全发给第一台，另外两台闲着；第一台一挂，全部失败。

**解决思路**：按策略（轮询、随机、权重、最少连接）把请求分散到多个实例。

```
请求1 → 实例A
请求2 → 实例B
请求3 → 实例C
请求4 → 实例A ...
```

**白话**：餐厅排队叫号，哪张桌子空出来就安排到哪张，别都挤在一个窗口。

---

### ④ 熔断降级

**问题**：订单服务响应变慢（比如数据库卡住），用户服务等它、网关等用户服务、前端等网关——**一个服务出问题，整条链路被拖死**，这叫雪崩。

**不解决**：一个慢服务拖垮整个系统。

**解决思路**：

- **熔断**：发现对方连续失败，就"跳闸"，一段时间内直接快速失败，不再傻等
- **降级**：失败时返回兜底数据（如"服务繁忙，请稍后再试"或缓存数据）

```
正常：A → B → C
B 故障：A → B（快速失败）→ 返回兜底结果，不拖累 A 的其他功能
```

**白话**：保险丝。电流异常就自动断开，保护整个电路，而不是等火烧起来。

---

### ⑤ 网关路由

**问题**：前端要调用 10 个微服务，难道要记 10 个域名和端口？鉴权、限流、跨域、日志要在每个服务里各写一遍？

**不解决**：前端耦合所有服务地址；公共逻辑重复建设；服务地址一变前端就得改。

**解决思路**：所有外部请求先到网关，由网关统一：

- 路由转发（`/api/order/**` → 订单服务）
- 鉴权（校验 token）
- 限流、跨域、日志、灰度发布

```
前端 ──▶ 网关 ──┬──▶ 用户服务
                ├──▶ 订单服务
                └──▶ 通知服务
```

**白话**：小区大门。外人只认大门，不直接进各家各户；保安（鉴权）也守在大门。

---

### ⑥ 统一配置

**问题**：10 个服务，每个都有数据库地址、Redis 地址、开关配置。改一个配置要改 10 个文件、重启 10 个服务？

**不解决**：配置散落、环境不一致、改配置成本高、容易漏改。

**解决思路**：配置集中存放在配置中心，服务启动时拉取；支持动态刷新（不重启生效）。

```
配置中心（Nacos Config）
   ├── user-service-dev.yml
   ├── order-service-dev.yml
   └── ...
        ▲ 启动拉取 / 变更推送
   各个微服务
```

**白话**：公司统一发的"员工手册"，改一版所有人同步更新，不用各自手抄。

---

### ⑦ 分布式事务

**问题**：下单要同时做两件事——订单服务写订单、库存服务扣库存。订单写成功、库存扣失败，怎么办？单个数据库的 `@Transactional` 管不了两个服务。

**不解决**：数据不一致（订单有了、库存没扣，超卖）。

**解决思路**：分布式事务方案（2PC、TCC、Saga、消息最终一致等），常用 Seata。

**白话**：两家银行转账，不能"我这边扣了、你那边没到账"。要么都成功，要么都回滚，或者通过补偿机制最终一致。

> 这是七大问题里**最复杂**的一个。实际项目中优先通过业务设计规避（如最终一致 + 幂等 + 对账），不要一上来就硬上强一致分布式事务。

---

## 4. 不是每个项目都要七个全上

### 按阶段引入

| 阶段 | 通常需要 |
|------|---------|
| 刚拆微服务 | 注册发现 + 服务调用 + 网关 |
| 流量上来 | 加负载均衡 + 熔断降级 |
| 服务变多 | 加统一配置 |
| 跨服务写数据 | 才需要分布式事务 |

> **组件是药，不是饭**。没病别吃药——没有跨服务事务需求，就不用引入 Seata；没有配置管理痛点，就不用急着上配置中心。

### 判断标准

```
这个问题现在真的发生了吗？
  否 → 先别引入，保持简单
  是 → 再选组件解决
```

| 问题 | 后续会学的方向 |
|------|---------------|
| 注册发现 + 配置 | Nacos |
| 服务调用 | OpenFeign |
| 负载均衡 | Spring Cloud LoadBalancer |
| 熔断降级 | Sentinel |
| 网关 | Spring Cloud Gateway |
| 分布式事务 | Seata |

---

## 6. 关键要点总结

| 要点 | 说明 |
|------|------|
| ✅ 七大问题 | 注册发现、服务调用、负载均衡、熔断降级、网关、配置、分布式事务 |
| ✅ 根源 | 进程内方法调用变成跨网络调用 |
| ✅ 每个问题都有代价 | 不解决就超时、雪崩、配置混乱、数据不一致 |
| ✅ 按需引入 | 不是所有项目都要七件套 |
| ✅ 先问题后组件 | 知道为什么用，比记住怎么配更重要 |
| ✅ 分布式事务最复杂 | 优先用业务设计规避，别硬上强一致 |
