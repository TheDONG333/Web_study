# 01.1 微服务 vs 单体架构：为什么要拆，拆了有什么代价

> **学习目标**
> - 说清单体架构和微服务架构各是什么
> - 记住两者的优缺点和适用场景
> - 理解"微服务不是升级，而是取舍"
> - 知道什么时候**不该**上微服务

---

## 1. 白话理解：一家餐厅的两种开法

**单体架构** = 一家大餐厅：后厨、收银、采购、保洁全在一个店里，所有人归一个店长管。

- 好处：沟通方便、出了问题一眼能看到、开业快
- 坏处：想换掉某个厨师，可能整家店要停业；生意好了只能把整家店扩大，不能只扩后厨

**微服务架构** = 一条美食街：每家店只做一件事（一家只做面、一家只做烧烤），各自独立经营。

- 好处：哪家店要装修，其他店照常营业；哪家生意好，单独扩店
- 坏处：店与店之间要协调（客人点面又点烧烤）、管理成本高、任何一家店关门都会影响整条街

> **一句话**：微服务不是"更先进的单体"，而是**用分布式复杂度换独立性和扩展性**。

---

## 2. 单体架构：一个应用装下所有功能

### 长什么样

```
user-management.war / app.jar
├── Controller（用户、订单、商品、支付……）
├── Service（所有业务逻辑）
├── Mapper（所有 SQL）
└── 一个数据库
        │
        ▼
   部署在一台服务器 / 一个 Tomcat
```

你前面写的 SSM 用户管理系统，就是典型的单体。

### 优点

| 优点 | 白话 |
|------|------|
| 开发简单 | 一个项目、一套代码，新人上手快 |
| 调用简单 | Service 之间直接方法调用，没有网络 |
| 事务简单 | 一个 `@Transactional` 管到底 |
| 部署简单 | 打一个包，扔到服务器上跑 |
| 排查简单 | 一个日志文件、一个进程，问题好定位 |

### 缺点（规模大了才明显）

| 缺点 | 白话 |
|------|------|
| 代码耦合 | 改一个模块，可能影响别的模块 |
| 发布牵连 | 改一行代码，整个应用重新打包发布 |
| 扩展浪费 | 只有订单模块压力大，也得把整个应用多部署几份 |
| 技术栈锁定 | 整个项目只能用一套技术 |
| 故障扩散 | 一个模块内存泄漏，整个应用一起挂 |
| 团队协作冲突 | 人多了，改同一个仓库容易互相踩脚 |

---

## 3. 微服务架构：按业务拆成多个独立服务

### 长什么样

```
             ┌─────────────┐
             │  网关 Gateway │
             └──────┬──────┘
        ┌───────────┼───────────┐
        ▼           ▼           ▼
   用户服务      订单服务      通知服务
   user-db      order-db     notify-db
   （独立部署）  （独立部署）  （独立部署）
```

每个服务：

- 一个独立项目、独立进程、独立部署
- 有自己的数据库（或独立 schema）
- 通过 HTTP / RPC 互相调用
- 可以独立扩容、独立升级、独立选技术栈

### 优点

| 优点 | 白话 |
|------|------|
| 独立部署 | 改订单服务，不影响用户服务 |
| 独立扩展 | 哪个服务压力大就扩哪个 |
| 故障隔离 | 一个服务挂了，其他服务还能工作（配合熔断） |
| 技术自由 | 不同服务可以用不同技术栈 |
| 团队自治 | 一个团队负责一个服务，边界清晰 |

### 代价（必须知道）

| 代价 | 白话 |
|------|------|
| 网络调用不可靠 | 方法调用不会失败，HTTP 调用会超时、会断 |
| 分布式事务 | 跨服务写数据，没有单个 `@Transactional` 能管 |
| 运维复杂 | 服务多了，部署、监控、日志、配置都成倍增加 |
| 排查困难 | 一个请求经过 5 个服务，出问题要跨服务追踪 |
| 数据一致性 | 只能做到"最终一致"，中间可能短暂不一致 |
| 重复建设 | 每个服务都要处理鉴权、日志、异常等公共逻辑 |

> **重点**：这些代价在单体里**根本不存在**。微服务不是免费的。

---

## 4. 一张表看清区别

| 维度 | 单体 | 微服务 |
|------|------|--------|
| 代码组织 | 一个项目 | 多个独立项目 |
| 部署 | 整体打包部署 | 每个服务独立部署 |
| 服务间调用 | 方法调用（进程内） | HTTP / RPC（跨网络） |
| 数据库 | 通常一个库 | 每个服务独立库 |
| 事务 | 本地事务 | 分布式事务 |
| 扩展 | 整体扩容 | 按服务扩容 |
| 故障影响 | 一处挂全挂 | 可隔离（需治理） |
| 运维成本 | 低 | 高 |
| 适合团队规模 | 小团队 | 多团队 / 大团队 |

---

## 5. 什么时候该用微服务？

### 适合

- 团队规模大（多个小组并行开发）
- 业务边界清晰，能拆成相对独立的领域
- 某些模块有独立的高并发/扩展需求
- 发布频率高，需要独立上线
- 公司有成熟的运维、监控、CI/CD 能力

### 不适合

| 情况 | 原因 |
|------|------|
| 初创项目、业务还在验证 | 业务边界没稳定，拆了就得反复重构 |
| 5~10 人小团队 | 沟通成本低，单体效率更高 |
| 没有运维/监控能力 | 服务多了管不过来，故障定位都难 |
| 强事务一致性要求 | 分布式事务复杂度和成本很高 |
| 流量很小 | 微服务带来的收益远小于成本 |

> 业界经验（Martin Fowler 的 "Monolith First"）：**先用单体把业务跑通，等痛点真的出现了再拆**。不要为了简历或时髦上微服务。

---

## 6. 演进的正确姿势

```
阶段一：单体
  一个 Spring Boot 项目，快速迭代
        │
        ▼ 业务变复杂、团队变大
阶段二：模块化单体
  还是一个项目，但按业务分模块（user / order / notify），模块间只通过接口调用
        │
        ▼ 某些模块需要独立部署/扩容
阶段三：微服务
  把模块拆成独立服务，引入注册中心、网关、配置中心等治理组件
```

> **模块化单体**是被很多人忽略的中间态：**不改部署方式，先把代码边界理清**。边界清不好的项目，拆成微服务只会更乱。

---

## 7. 关键要点总结

| 要点 | 说明 |
|------|------|
| ✅ 单体优点 | 简单、快、事务简单、排查容易 |
| ✅ 单体缺点 | 耦合、发布牵连、扩展浪费、故障扩散 |
| ✅ 微服务优点 | 独立部署、独立扩展、故障隔离、团队自治 |
| ✅ 微服务代价 | 网络不可靠、分布式事务、运维复杂、排查困难 |
| ✅ 选型看阶段 | 小团队/业务未稳先用单体，痛点出现再拆 |
| ✅ 演进路径 | 单体 → 模块化单体 → 微服务 |
| ✅ 核心认知 | 微服务是取舍，不是升级 |
