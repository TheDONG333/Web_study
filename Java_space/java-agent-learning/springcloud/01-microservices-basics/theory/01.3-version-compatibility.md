# 01.3 Spring Cloud 与 Spring Boot 版本对应：90% 报错的根源

> **学习目标**
> - 理解 Spring Cloud 的"版本列车"机制
> - 记住 Spring Cloud 与 Spring Boot 的对应关系
> - 会用 BOM 管理依赖，不给单个 starter 写版本
> - 能根据报错判断是不是版本问题

---

## 1. 白话理解：版本列车，一列车配一条轨道

Spring Cloud 不是"一个框架"，而是**一组组件的集合**（网关、负载均衡、配置、熔断……）。这些组件必须一起发布、一起升级，所以官方把它们打包成一个个"**版本列车**"（Release Train）。

每列列车只适配特定版本的 Spring Boot：

```
Spring Cloud 2025.0.x  ═══▶ 只能跑在 Spring Boot 3.5.x 上
Spring Cloud 2024.0.x  ═══▶ 只能跑在 Spring Boot 3.4.x 上
Spring Cloud 2023.0.x  ═══▶ 只能跑在 Spring Boot 3.2.x / 3.3.x 上
```

**坐错车 = 启动报错、类找不到、方法不存在、配置不生效。**

> **核心规则**：**先选 Spring Cloud 版本，再由它决定 Spring Boot 版本**。反过来选（先随便定 Boot，再挑 Cloud）就是 90% 报错的来源。

## 3. 正确姿势：用 BOM 统一管理版本

### 白话理解

BOM（Bill of Materials）是一张"**版本清单**"：你导入它，Spring Cloud 所有组件的版本就都定好了，**你不需要给每个 starter 写 version**。

```xml
<properties>
    <java.version>26</java.version>
    <spring-cloud.version>2025.0.0</spring-cloud.version>
</properties>

<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.cloud</groupId>
            <artifactId>spring-cloud-dependencies</artifactId>
            <version>${spring-cloud.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
```

之后引入组件，**不写版本号**：

```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-gateway</artifactId>
</dependency>
```

> 版本由 BOM 决定。你手写一个版本，反而可能和 BOM 冲突——**画蛇添足**。

### 三层版本关系

```
Spring Boot parent（3.5.x）
        │ 决定 Boot 自身和官方 starter 版本
        ▼
Spring Cloud BOM（2025.0.x）
        │ 决定 Cloud 组件版本
        ▼
Spring Cloud Alibaba BOM（对应版本）
        │ 决定 Nacos / Sentinel / Seata 等版本
```

## 4. 版本不匹配的典型报错

| 报错 | 含义 | 排查方向 |
|------|------|---------|
| `NoSuchMethodError` | 运行时调用了不存在的方法 | 依赖版本比代码期望的旧/新 |
| `NoClassDefFoundError` | 找不到某个类 | 组件版本和 Boot 版本不匹配 |
| `NoClassDefFoundError: javax/servlet/...` | 用了 Boot 2 时代的依赖 | Boot 3 已改成 `jakarta.servlet` |
| `Spring MVC found on classpath, which is incompatible with Spring Cloud Gateway` | 网关项目里同时引了 `spring-boot-starter-web` | Gateway 基于 WebFlux，不能和 MVC 混用 |
| `No spring.config.import property has been defined` | Boot 2.4+ 外部配置需要显式导入 | 加 `spring.config.import`（配置中心模块再讲） |
| `Failed to bind properties under 'spring.cloud...'` | 配置项在新版本改名/移除 | 查当前版本文档的配置键 |
| 启动直接失败，日志提示类版本/字节码错误 | 依赖代际混用 | 检查是否同时引入不同年份的 Cloud 组件 |

> **判断口诀**：**"类找不到、方法不存在、配置绑不上"——先怀疑版本，再看代码。**

## 5. 五条铁律

| # | 规则 | 说明 |
|---|------|------|
| 1 | Cloud 版本决定 Boot 版本 | 查官方兼容表，别凭感觉 |
| 2 | 用 BOM，不给单个 starter 写版本 | 避免版本打架 |
| 3 | 不混用不同代际的 Cloud 组件 | 2021 的组件别和 2025 的混在一起 |
| 4 | Alibaba 版本跟 Cloud 对齐 | 见 01.4 |
| 5 | 不确定就用 Spring Initializr 生成 | 它给出的组合一定兼容 |

### 一个实用技巧

新建微服务项目时，用 **start.spring.io**（或 IDEA 的 Spring Initializr）勾选依赖，它会自动生成**互相兼容**的 Boot + Cloud 版本。**不要从网上抄一份几年前的 pom**——那是最常见的踩坑方式。

## 7. 关键要点总结

| 要点 | 说明 |
|------|------|
| ✅ 版本列车 | Cloud 组件成套发布，只适配特定 Boot 版本 |
| ✅ 对应关系 | 2025.0.x→Boot 3.5.x；2024.0.x→3.4.x；2023.0.x→3.2/3.3 |
| ✅ 先 Cloud 后 Boot | 由 Cloud 反推 Boot，不能反过来 |
| ✅ BOM 管理 | 导入 `spring-cloud-dependencies`，starter 不写版本 |
| ✅ 典型报错 | NoSuchMethodError、NoClassDefFoundError、配置绑定失败 |
| ✅ 不确定就用 Initializr | 自动生成兼容组合 |
